# CADEX — Cadence API Contract (v1.1)

**What this is:** the exact shape of Cadence's side of CADEX, so The
Atrium can be built against it. This is the technical annex to
`CADEX_Integration_Proposal_v1.0.md` — read that first for the why; this
document is the how.

**Status:** Cadence's side of this contract is coded and ready to deploy,
but **not yet live**. Nothing will call The Atrium, and nothing is
listening for The Atrium to call Cadence, until both sides agree this
contract and switch it on.

**Changes from v1.0** (folding in Atrium's `CADEX_Atrium_Response_v1.0.md`,
all accepted as proposed):
- §3.3 `/api/v1/surgeons` gains per-theatre surgeon data and a weekend
  waiting-list surgeon — additive, answers Atrium's per-theatre-surgeon
  question. No new endpoint.
- §4.2 clarified: published-only data, the quarter-ish envelope Atrium
  can actually serve, and confirmation that empty objects/strings mean
  "nothing scheduled", not an error.
- §5 records Atrium's actual polling behaviour (fetch-on-view + ~60s
  cache, not a fixed background loop) — informational, doesn't change
  what Cadence exposes.
- New §7: value conventions for consultant fields (half-day splits,
  double-ups, cancelled/closed) — confirmed compatible with Cadence's
  existing no-match/empty-value fallback, no code change required.
- §2 base URLs: Atrium's production base confirmed as
  `https://theatrium.org.uk/api/v1/`.

---

## 1. Two independent connections

CADEX is two separate one-way pulls, not a shared database and not a
push/webhook:

| | Who calls | Calls whom | For |
|---|---|---|---|
| **A** | Cadence | The Atrium | Consultant anaesthetist allocations |
| **B** | The Atrium | Cadence | ODP allocations + surgeon on-call (incl. per-theatre) |

Each direction has its own API key. Cadence polls The Atrium roughly
once a minute (§5); The Atrium calls Cadence on-demand rather than on a
fixed loop (§5) — nothing pushes either way.

---

## 2. Authentication

Every request (except the unauthenticated status ping, see §3.1) carries:

```http
Authorization: Bearer <api-key>
```

Two separate keys, generated independently by whoever owns that side,
each revocable/rotatable on its own side without redeploy:

- **Cadence → Atrium key** — generated by Cadence, given to Craig. The
  Atrium checks this key on its `/api/v1/consultants` endpoint.
- **Atrium → Cadence key** — generated by Craig, given to Cadence. Cadence
  checks this key on its own `/api/v1/odp`, `/api/v1/surgeons` and
  authenticated `/api/v1/status` calls.

A missing or wrong key gets HTTP `401`. Keys are exchanged out of band
(in person or NHS mail), separately from the base URLs below.

**Base URLs:**
- Atrium production: `https://theatrium.org.uk/api/v1/`
- Cadence production: `https://<cadence-hosting-domain>/api/v1/`
  (confirmed once Cadence deploys — see `docs/CADEX_SETUP.md`)

A test window against non-production keys/environments is to be agreed
once both sides are ready to try a real exchange.

## 3. What Cadence exposes (direction B — Atrium calls Cadence)

All three endpoints take an optional `?week=YYYY-MM-DD` query param — any
date within the target week; Cadence snaps it to that week's Monday. If
omitted, defaults to the current week.

### 3.1 `GET /api/v1/status`

No auth required for a bare ping (reveals nothing department-specific).
Atrium's own `/api/v1/status` matches this: accepts both an authenticated
and a bare ping.

```json
{ "version": "v1", "status": "ok", "timestamp": "2026-08-03T09:00:00.000Z" }
```

### 3.2 `GET /api/v1/odp`

```json
{
  "weekCommencing": "2026-08-03",
  "lastUpdated": "2026-08-01T14:22:00.000Z",
  "published": true,
  "monday": {
    "theatres": {
      "Theatre 1": { "odp1": "J Smith", "odp2": "" },
      "Theatre 2": { "odp1": "A Jones", "odp2": "B Lee" },
      "Cath Lab":  { "odp1": "C Patel", "odp2": "" },
      "Theatre 4": { "odp1": "D Khan",  "odp2": "" },
      "Theatre 5": { "odp1": "E Ward",  "odp2": "" }
    },
    "onCallOdp": "F Brown",
    "onCallFromHome": false,
    "onCallExtra": ""
  },
  "tuesday": { "...": "same shape as monday" },
  "wednesday": { "...": "same shape as monday" },
  "thursday": { "...": "same shape as monday" },
  "friday": { "...": "same shape as monday" },
  "saturday": {
    "onCallOdp1": "G Hall", "onCallSession1": "ALL DAY",
    "onCallOdp2": "", "onCallSession2": "",
    "waitingListOdp": "H Young"
  },
  "sunday": { "...": "same shape as saturday" }
}
```

Notes:
- `theatres` only lists whichever of Theatre 1 / 2 / 4 / 5 / Cath Lab
  actually exist for this Cadence department — a department without a
  Cath Lab simply omits that key.
- Monday–Friday only. Cadence's weekend rota has no per-theatre columns,
  only the on-call/waiting-list fields shown under `saturday`/`sunday`.
- Empty string means "not yet filled in" — same "nothing to show"
  semantics Atrium confirmed for its own empty-string cases (§7).

### 3.3 `GET /api/v1/surgeons` — updated in v1.1

Now carries per-theatre surgeon assignment alongside on-call, answering
Atrium's per-theatre-surgeon question directly rather than needing a
fourth endpoint:

```json
{
  "weekCommencing": "2026-08-03",
  "lastUpdated": "2026-08-01T14:22:00.000Z",
  "published": true,
  "monday": {
    "cardiacOnCall": "Mr Adams",
    "thoracicOnCall": "Ms Baker",
    "theatres": {
      "Theatre 1": "Mr Adams",
      "Theatre 2": "Ms Baker",
      "Cath Lab":  "Mr Clarke"
    }
  },
  "tuesday":   { "...": "same shape as monday" },
  "wednesday": { "...": "same shape as monday" },
  "thursday":  { "...": "same shape as monday" },
  "friday":    { "...": "same shape as monday" },
  "saturday":  { "cardiacOnCall": "...", "thoracicOnCall": "...", "waitingListSurgeon": "..." },
  "sunday":    { "...": "same shape as saturday" }
}
```

Notes:
- `cardiacOnCall` / `thoracicOnCall` run all seven days, unchanged from
  v1.0.
- `theatres` (per-theatre operating surgeon) is Monday–Friday only, same
  theatre-name set and same "only theatres that exist" rule as `/odp`'s
  `theatres` object. A theatre with nobody assigned that day is simply
  omitted from the object, same "nothing to show" convention as
  elsewhere.
- `waitingListSurgeon` (Saturday/Sunday only) is the weekend equivalent —
  there's no per-theatre column at the weekend, only the one waiting-list
  slot.

## 4. What Cadence needs from The Atrium (direction A — Cadence calls Atrium)

### 4.1 `GET /api/v1/status`
Same shape as 3.1 — used for the "Test connection" button in Cadence's
admin panel. Cadence sends its key on this call.

### 4.2 `GET /api/v1/consultants?week=YYYY-MM-DD` — clarified in v1.1

Requested once a minute for the current week. Expected response:

```json
{
  "weekCommencing": "2026-08-03",
  "lastUpdated": "2026-08-03T08:30:00Z",
  "monday":    { "ct1": "PJ", "ct2": "SB", "ct3": "MC", "ct4": "JA", "ct5": "LC", "cl": "TG", "cicu": "VR", "onCall": "NM" },
  "tuesday":   { "ct1": "...", "ct2": "...", "ct3": "...", "ct4": "...", "ct5": "...", "cl": "...", "cicu": "...", "onCall": "..." },
  "wednesday": { "...": "..." },
  "thursday":  { "...": "..." },
  "friday":    { "...": "..." },
  "saturday":  { "ct5": "LC", "onCall": "NM", "cicu": "VR" },
  "sunday":    { "ct5": "...", "onCall": "...", "cicu": "..." }
}
```

- Every field is optional per day — Cadence only reads what's present.
- Values are unique two-letter capital initials, stable identifiers on
  Atrium's side, sent verbatim (confirmed by Atrium — same format
  everywhere in Atrium: grid, ICS feed, share link). Cadence still
  treats them as opaque strings on the wire; matching happens via each
  anaesthetist's own "CADEX initials" entry in Cadence's Staff Admin
  (unchanged from v1.0 §7/8).
- **Published data only.** Atrium serves published (and archived) rota
  data exclusively — no draft/provisional allocations will ever appear
  in this feed. Cadence's imported-data badges only ever show something
  Atrium itself has already committed to.
- **Coverage window:** reliably the current quarter plus the next once
  published (quarters compiled ~6 weeks ahead), and at least a year of
  history. A `week` outside that range returns empty objects, never an
  error — Cadence only ever requests the current week in practice (§5),
  so this is comfortably inside range, but worth knowing if that ever
  changes.
- **"Nothing scheduled"** is signalled by the day key being present with
  an empty object (not an omitted day, not an error) — matches what
  Cadence already does with its own "not yet filled in" empty strings.

### How Cadence maps this in

| Atrium field | Cadence target | Rule |
|---|---|---|
| `ct1` | Theatre 1 anaesthetist | Direct, Mon–Fri |
| `ct2` | Theatre 2 anaesthetist | Direct, Mon–Fri |
| `ct3` | Cath Lab anaesthetist | **Thursday only** |
| `ct4` | Theatre 4 anaesthetist | Direct, Mon–Fri |
| `ct5` | Theatre 5 anaesthetist | Direct, Mon–Fri |
| `ct5` | Waiting List anaesthetist | Sat/Sun instead of Theatre 5 |
| `cl` | Cath Lab anaesthetist | Direct, Mon–Fri except Thursday (see `ct3`) |
| `cicu` | New CICU line on Cadence's on-call display | Direct, every day |
| `onCall` | On-call anaesthetist | Direct, every day |

Unchanged from v1.0 — repeated here so it stays unambiguous which of
`ct3`/`cl` wins on a Thursday (`ct3`, falling back to `cl` if blank).

## 5. Sync behaviour

- **Cadence → Atrium:** polls `/api/v1/consultants` roughly **every 60
  seconds**, no user interaction. On failure (network error, non-200, bad
  JSON) Cadence keeps whatever it last successfully imported, logs the
  failure, and retries next cycle — never blanks out previously-imported
  data.
- **Atrium → Cadence:** confirmed as **fetch-on-view**, not a fixed
  background loop — Atrium calls `/api/v1/odp` and `/api/v1/surgeons`
  when a user opens a screen that shows the data, through a short
  (~60s) server-side cache, plus manual refresh. This needs no change on
  Cadence's side; Cadence's endpoints are cheap reads and handle
  on-demand traffic fine (§6).
- **Imports never auto-overwrite.** On Cadence's side, imported
  consultant data shows as a "from The Atrium" badge with an Apply
  button — never written automatically. Atrium confirmed the mirror
  behaviour for Cadence-owned data appearing in Atrium: shown with
  visible "from Cadence" provenance, never overwrites a manual Atrium
  entry, local entry wins on conflict. Cadence remains sole owner of
  ODP/surgeon data; Atrium remains sole owner of consultant data — matches
  guiding principles 1, 2 and 7–9 in the original proposal.

---

## 6. Timeouts & rate

- Cadence's own requests to The Atrium time out after **10 seconds**,
  comfortably within Atrium's stated capacity.
- Cadence's Provider endpoints (§3.2/3.3) are cheap single-document reads
  and handle on-demand polling (§5) without any special-casing.

## 7. Value conventions for consultant fields (new in v1.1)

Atrium theatre-days don't always reduce to one clean name. Agreed
conventions, all of which already fall through Cadence's existing
"no match → show raw string with a warning, never guess" behaviour with
no code change required:

| Atrium situation | String sent | Cadence behaviour |
|---|---|---|
| One consultant, full day | `CD` | Auto-matches via Staff Admin initials |
| Half-day split (rare) | `CD am / SE pm` | Won't match any single initials — shows the raw string with a "no match" warning, which is the correct outcome |
| Double-up (two consultants, one list) | Primary's initials only | Auto-matches |
| List cancelled | `""` (empty) | Field left unfilled — no badge shown at all |
| Closed / no list / gap | `""` (empty) | Field left unfilled — no badge shown at all |

Confirmed: empty string means "nothing to show" in all three of the last
cases, matching Cadence's own "not yet filled in" semantics exactly.

---

## 8. Consultant initials — matched automatically on Cadence's side

Cadence resolves whatever string arrives in `ct1`–`ct5`/`cl`/`onCall`/`cicu`
against each anaesthetist's own "CADEX initials" set in Cadence's Staff
Admin (case-insensitive). A match applies the anaesthetist's full Cadence
name to the rota automatically; no match falls back to showing the raw
string with a "no match" warning rather than guessing (§7 covers when
that's expected to happen deliberately).

The definitive initials-to-name list will travel with the key exchange
(§2), not in this document, so the pairing isn't separated from the
credentials it depends on.

---

## 9. Sequencing

Following the original proposal's four-stage deployment, Atrium's
proposed order (accepted):

1. Atrium builds its provider (`/api/v1/status`, `/api/v1/consultants`) —
   independent of other Atrium work in progress.
2. Cadence tests its consumer against it with exchanged test keys.
3. Atrium's consumer of `/api/v1/odp` and `/api/v1/surgeons` lands with
   Atrium's theatre-team board feature (currently in testing).
4. Production keys and go-live once both sides match.

Status on both sides as of this document: nothing is deployed or live
yet. Cadence's provider + consumer are coded and ready (see
`docs/CADEX_SETUP.md`); Atrium's provider work starts once this v1.1 is
confirmed.
