# CADEX — Cadence API Contract (v1.0)

**What this is:** the exact shape of Cadence's side of CADEX, so The
Atrium can be built against it. This is the technical annex to
`CADEX_Integration_Proposal_v1.0.md` — read that first for the why; this
document is the how.

**Status:** Cadence's side of this contract is coded and ready to deploy,
but **not yet live**. Nothing will call The Atrium, and nothing is
listening for The Atrium to call Cadence, until both sides agree this
contract and switch it on.

---

## 1. Two independent connections

CADEX is two separate one-way pulls, not a shared database and not a
push/webhook:

| | Who calls | Calls whom | For |
|---|---|---|---|
| **A** | Cadence | The Atrium | Consultant anaesthetist allocations |
| **B** | The Atrium | Cadence | ODP allocations + surgeon on-call |

Each direction has its own API key. Each side polls the other roughly
once a minute — nothing pushes.

---

## 2. Authentication

Every request (except the unauthenticated status ping, see 3.1) carries:

```http
Authorization: Bearer <api-key>
```

Two separate keys, generated independently by whoever owns that side:

- **Cadence → Atrium key** — generated by Cadence, given to Craig. The
  Atrium must check this key on its `/api/v1/consultants` endpoint.
- **Atrium → Cadence key** — generated by Craig, given to Cadence. Cadence
  checks this key on its own `/api/v1/odp`, `/api/v1/surgeons` and
  authenticated `/api/v1/status` calls.

A missing or wrong key gets HTTP `401`.

---

## 3. What Cadence exposes (direction B — Atrium calls Cadence)

Base URL: `https://<cadence-hosting-domain>/api/v1/`

All three endpoints take an optional `?week=YYYY-MM-DD` query param — any
date within the target week; Cadence snaps it to that week's Monday. If
omitted, defaults to the current week.

### 3.1 `GET /api/v1/status`

No auth required for a bare ping (reveals nothing department-specific).

```json
{ "version": "v1", "status": "ok", "timestamp": "2026-08-03T09:00:00.000Z" }
```

### 3.2 `GET /api/v1/odp`

```json
{
  "weekCommencing": "2026-08-03",
  "lastUpdated": "2026-08-01T14:22:00.000Z",
  "published": true,
  "monday": {
    "theatres": {
      "Theatre 1": { "odp1": "J Smith", "odp2": "" },
      "Theatre 2": { "odp1": "A Jones", "odp2": "B Lee" },
      "Cath Lab":  { "odp1": "C Patel", "odp2": "" },
      "Theatre 4": { "odp1": "D Khan",  "odp2": "" },
      "Theatre 5": { "odp1": "E Ward",  "odp2": "" }
    },
    "onCallOdp": "F Brown",
    "onCallFromHome": false,
    "onCallExtra": ""
  },
  "tuesday": { "...": "same shape as monday" },
  "wednesday": { "...": "same shape as monday" },
  "thursday": { "...": "same shape as monday" },
  "friday": { "...": "same shape as monday" },
  "saturday": {
    "onCallOdp1": "G Hall", "onCallSession1": "ALL DAY",
    "onCallOdp2": "", "onCallSession2": "",
    "waitingListOdp": "H Young"
  },
  "sunday": { "...": "same shape as saturday" }
}
```

Notes:
- `theatres` only lists whichever of Theatre 1 / 2 / 4 / 5 / Cath Lab
  actually exist for this Cadence department — a department without a
  Cath Lab simply omits that key.
- Monday–Friday only. Cadence's weekend rota has no per-theatre columns,
  only the on-call/waiting-list fields shown under `saturday`/`sunday`.
- Empty string means "not yet filled in", not "no such role".

### 3.3 `GET /api/v1/surgeons`

```json
{
  "weekCommencing": "2026-08-03",
  "lastUpdated": "2026-08-01T14:22:00.000Z",
  "published": true,
  "monday":    { "cardiacOnCall": "Mr Adams",  "thoracicOnCall": "Ms Baker" },
  "tuesday":   { "cardiacOnCall": "...", "thoracicOnCall": "..." },
  "wednesday": { "...": "..." },
  "thursday":  { "...": "..." },
  "friday":    { "...": "..." },
  "saturday":  { "...": "..." },
  "sunday":    { "...": "..." }
}
```

All seven days — cardiac/thoracic on-call runs every day, not just
weekdays.

## 4. What Cadence needs from The Atrium (direction A — Cadence calls Atrium)

Cadence expects The Atrium to expose:

### 4.1 `GET /api/v1/status`
Same shape as 3.1 — used for the "Test connection" button in Cadence's
admin panel. Cadence sends its key on this call (unlike its own status
endpoint, which allows an anonymous ping).

### 4.2 `GET /api/v1/consultants?week=YYYY-MM-DD`

This is the one endpoint Cadence actually needs. Requested once a minute
for the current week. Expected response:

```json
{
  "weekCommencing": "2026-08-03",
  "lastUpdated": "2026-08-03T08:30:00Z",
  "monday":    { "ct1": "PJ", "ct2": "SB", "ct3": "MC", "ct4": "JA", "ct5": "LC", "cl": "TG", "cicu": "VR", "onCall": "NM" },
  "tuesday":   { "ct1": "...", "ct2": "...", "ct3": "...", "ct4": "...", "ct5": "...", "cl": "...", "cicu": "...", "onCall": "..." },
  "wednesday": { "...": "..." },
  "thursday":  { "...": "..." },
  "friday":    { "...": "..." },
  "saturday":  { "ct5": "LC", "onCall": "NM", "cicu": "VR" },
  "sunday":    { "ct5": "...", "onCall": "...", "cicu": "..." }
}
```

- Every field is optional per day — Cadence only reads what's present,
  and ignores unrecognised extra fields, so The Atrium is free to send
  the same full 8-field object every day even though Cadence only uses
  `ct1`/`ct2`/`ct3`/`ct4`/`cl` on weekdays.
- Values are whatever short name/initials The Atrium uses for a
  consultant — Cadence treats them as opaque strings, doesn't try to
  match them against its own staff list.
- If Craig's Atrium can't produce data for the exact requested `week`,
  responding with an empty object for that day (rather than omitting the
  day, or erroring) is the cleanest "nothing scheduled" signal.

### How Cadence maps this in

| Atrium field | Cadence target | Rule |
|---|---|---|
| `ct1` | Theatre 1 anaesthetist | Direct, Mon–Fri |
| `ct2` | Theatre 2 anaesthetist | Direct, Mon–Fri |
| `ct3` | Cath Lab anaesthetist | **Thursday only** |
| `ct4` | Theatre 4 anaesthetist | Direct, Mon–Fri |
| `ct5` | Theatre 5 anaesthetist | Direct, Mon–Fri |
| `ct5` | Waiting List anaesthetist | Sat/Sun instead of Theatre 5 |
| `cl` | Cath Lab anaesthetist | Direct, Mon–Fri except Thursday (see `ct3`) |
| `cicu` | New CICU line on Cadence's on-call display | Direct, every day |
| `onCall` | On-call anaesthetist | Direct, every day |

This is exactly section 18 of the original proposal — repeated here so
it's unambiguous which of `ct3`/`cl` wins on a Thursday (answer: `ct3`,
falling back to `cl` if `ct3` is blank that day).

## 5. Sync behaviour

- Cadence polls The Atrium's `/api/v1/consultants` roughly **every 60
  seconds**, no user interaction.
- If a poll fails (network error, non-200, bad JSON) Cadence keeps
  whatever it last successfully imported, logs the failure, and retries
  on the next cycle — it never blanks out previously-imported data.
- Imports never overwrite anything already saved in Cadence's own rota
  automatically. They show up as a "from The Atrium" badge next to the
  relevant field, and a person has to click Apply — so a local change
  can never be silently clobbered by a stale or wrong import.
- Cadence does not push anything to The Atrium. If The Atrium wants to
  show ODP/surgeon data live, it needs to poll Cadence's endpoints (3.2,
  3.3) on its own schedule — a similar ~60s interval would keep both
  sides consistent, but the actual interval is entirely The Atrium's
  choice.

---

## 6. Timeouts & rate

- Cadence's own requests to The Atrium time out after **10 seconds**.
- Cadence's Provider endpoints (3.2/3.3) are cheap single-document reads
  and should comfortably handle a request every few seconds if The
  Atrium wants to poll faster than once a minute.
